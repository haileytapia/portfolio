# Azure AI Search agent skill
{: .no_toc }

My team used an internal AI tooling suite, which I'll call DocAssist here, to support documentation work across planning, research, authoring, review, and evaluation. PMs also increasingly used it to generate documentation PRs.

DocAssist was broadly useful, but it was designed around the product area most writers on my team documented. Azure AI Search had its own technical and documentation practices that weren't represented in the workflow. For this reason, I decided to extend DocAssist with the product-specific knowledge it needed to effectively support the Azure AI Search documentation.

## Where DocAssist fell short

Whether I used DocAssist to draft content myself or reviewed a PR generated by a PM, I had to make substantial product-specific corrections before the content was ready to publish. These corrections ranged from code and API versions to content placement, metadata, and reuse.

### Code and SDK conventions

+ It couldn't reliably evaluate code snippets because it wasn't configured to load the SDK packages used by Azure AI Search.

+ It could add unnecessary scaffolding to simple snippets or introduce patterns that didn't match the surrounding examples.

### Documentation strategy and structure

+ It could place new content in the wrong article rather than recognizing when an existing article should be extended or when a change belonged in a "What's New" announcement.

+ It could duplicate information instead of preserving a single source of truth.

+ It didn't consistently account for the side-by-side preview and GA tabs often used in documentation.

### Product and repository conventions

+ It didn't reliably apply Azure AI Search's API version conventions, such as documenting the latest version by default while preserving older references when needed.

+ It could explicitly assign me as an author, even though our global DocFX configuration already made me the default author for the Azure AI Search documentation.

+ It could use metadata values that didn't follow our contributor guidance.

## New Azure AI Search agent skill

As part of the Microsoft Global Hackathon 2026, I created an agent skill that encoded more than 20 Azure AI Search–specific documentation rules and decision points. Rather than replacing DocAssist, I designed the skill as a layer on top of its existing capabilities, supplying the Azure AI Search context the underlying system was missing.

The skill captured decisions that had previously depended heavily on writer expertise, including:

+ **Content placement:** When to create a new article, extend an existing article, or limit a change to a "What's New" announcement.

+ **API versions:** How to handle Azure AI Search's date-based versions, including documenting the latest version by default while preserving older references when historical accuracy requires them.

+ **Authorship metadata:** How to apply our DocFX configuration and authorship conventions.

+ **Preview disclosures:** How to apply the [preview disclosure model](preview-disclosure-model.md) I developed separately, including the shared include and criteria for applying `(preview)` labels.

+ **Code and SDK conventions:** How to structure code snippets, use the appropriate SDK packages, and maintain consistency with surrounding prose and snippets.

+ **Content reuse:** When to preserve or extend a single source of truth rather than duplicate information.

## Guiding principle: Start with the customer

I designed the skill around a simple principle: start with the customer's need, goal, or task.

Rather than allowing a one-pager, spec, or feature description to determine the structure of the documentation, the skill used the customer's task as the basis for subsequent decisions. This helped DocAssist identify not only what information had changed but also what documentation would best help customers accomplish their tasks.

## Impact

The skill turned Azure AI Search-specific documentation expertise from individual writer judgment into an explicit, reusable layer of the AI-assisted workflow. Decisions that had previously depended on a writer recognizing a product-specific issue could now be represented as rules and decision points DocAssist could apply consistently.

This work also changed how I worked with AI tooling. I started as a user of the existing system and became an active contributor to how it behaved: defining documentation requirements, testing the skill against real authoring scenarios, examining where its outputs still fell short, and iterating on the rules and decision points. That gave me a much more practical understanding of how to evaluate and refine AI-assisted workflows rather than simply use them.

Most importantly, this work changed how I think about AI-assisted documentation. It's not just about generating better text. Effective AI-assisted documentation also needs to account for the product's documentation system, the customer's task, and the judgment writers apply to structure, reuse, and quality.
